title: "Security boundaries"
description: "Understand workspace isolation, credentials, and application access."
---

Rigbox runs workspaces in separate Firecracker micro-VMs. Isolation boundaries and application credentials are different concerns: an app can read the credentials you deliberately provide to it.

## VM-level isolation

Each workspace has its own guest kernel and root filesystem. Workspace apps share that VM; app releases do not create a separate micro-VM for each app. Treat workspace administrators and code with guest root access as trusted with that workspace's contents.

The platform uses network and service authorization boundaries in addition to VM isolation. Do not interpret a VM boundary as a guarantee that all outbound network access is blocked or that malicious code cannot contact public APIs.

## Credential protection

### Platform secrets

Control-plane credentials are not required in ordinary workspace code. VM-local Rigbox services use the workspace's bridge-network identity, scoped to its compute node, rather than a personal account key copied into the guest.

The CLI inside a workspace uses this ambient identity for supported workspace-scoped commands. Use the [execution-mode reference](/cli-reference/execution-modes) for its actual command surface.

### AI provider keys

[Managed AI](/guides/managed-proxy) routes requests through the platform proxy without requiring your provider key in application code. [BYOK](/guides/byok) means supplying credentials for your own provider. If a credential is injected into the guest or application's environment, code there can read it. Do not claim that environment injection makes a secret inaccessible or guarantees it never reaches disk.

Application `secrets:` are deployment inputs, not a promise of an encrypted application secret store. Treat environment output, app metadata, logs, and process access as potential disclosure paths.

### API keys

Personal `rb_` API keys grant account access. Keep them on a trusted local machine or backend, rotate them when exposed, and never distribute your own key to end-user browser code or an untrusted workspace.

GitHub deployment credentials are a distinct short-lived credential flow bound to a repository/workspace. They are not interchangeable with personal account keys.

## App access control

Private, public, and email-restricted app visibility governs access through the app route. It does not isolate apps sharing a workspace or secure a database against other code with local access. Apply application authentication when your own product needs it.

For programmatic access to a private route, use an authorized key as described in [authentication](/cli-reference/authentication). A valid key alone does not grant access to every owner's app.

## SSH authentication

Register public keys and connect to the target returned by `rig workspace ssh-info`. The workspace SSH path and the separate SSH TUI gateway are different. Do not infer the host, username, or port from an old infrastructure diagram.

## Network model

Workspace apps can make outbound connections for dependencies and supported services. The managed proxy is a bridge-local service with its own identity checks. Public API calls and private app requests have separate authentication rules.

## Rate limiting

Handle rate-limit responses using the endpoint's returned guidance and bounded backoff. Use [effective resource limits](/concepts/limits) rather than assuming a fixed numeric table applies to every account and endpoint.

## App release integrity

Managed source and dependency caches are protected from ordinary app writes and checked during reuse and activation. This is not protection against a workspace administrator with root access. Rollback restores retained app code/configuration, not application data or a compromised whole workspace.
