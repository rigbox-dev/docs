---
title: Persistent Volumes
description: Durable ext4 storage that survives redeploys and stop→start — the right home for SQLite databases, uploads, and logs.
---

A persistent volume is an ext4 drive attached to a workspace as a **second disk**, separate from the workspace's root filesystem. It keeps application data separate from managed app releases and workspace image replacement.

## Why you need one

In v0.13, incremental deployment prepares application code in managed release directories. Those directories are not durable writable storage. Put databases, uploads, and other mutable files on a data volume instead of beside source code.

Durable state belongs on a persistent volume. The usual convention is a volume named `data` mounted at `/home/developer/data`, exposed to the app as `DATA_DIR`:

```yaml
env:
  DATA_DIR: /home/developer/data
```

Store SQLite databases, uploaded files, and logs under `$DATA_DIR` and they stay put across deploys.

<Note>
A persistent volume survives **app redeploys**, **app restarts**, and **stop→start** of the workspace. It is destroyed only when you delete the volume or the workspace itself.
</Note>

## Declare a volume in rig.yaml

The canonical path is to declare durable disks once under `workspace.volumes`, then opt each app into the mount with `volumes: [data]`. Only apps that reference a volume receive the mount.

A deploy doesn't create volumes. A workspace that has no volumes gets a 1024 MiB `data` volume at `/home/developer/data` when it first boots. Any other volume has to exist before you deploy an app that uses it, because volumes attach when the workspace boots: stop the workspace, create the volume with [`rig volume create`](#manage-volumes-with-the-cli), then start it and deploy. A deploy that references a volume the workspace doesn't have is refused with the volume's name.

```yaml
name: markdown-notes
port: 8080
workspace:
  volumes:
    - name: data
      mountPath: /home/developer/data
      sizeMb: 1024
install: pip install --break-system-packages flask gunicorn
start: gunicorn --bind 0.0.0.0:8080 app:app
health: { path: /healthz, timeoutSeconds: 30 }
volumes: [data]
env:
  DATA_DIR: /home/developer/data
```

Point `DATA_DIR` at the same path and your app reads and writes durable state there.

For multi-app projects, keep the declaration at the workspace level and attach it only to the apps that need it:

```yaml
workspace:
  image: base
  volumes:
    - name: data
      mountPath: /home/developer/data
      sizeMb: 1024

apps:
  api:
    path: ./api
    port: 5100
    start: npm start
    volumes: [data]
    env:
      DATA_DIR: /home/developer/data

  web:
    path: ./web
    port: 5101
    start: npm start
    dependsOn: [api]
    visibility: public
```

App references can be written as `volumes: [data]` or `volumes: [{ name: data }]`. App-local full specs are still supported for single-app or one-off cases:

```yaml
volumes:
  - name: data
    mountPath: /home/developer/data
    sizeMb: 1024
```

## Each app gets its own folder

A volume is private to each app by default. Each app that mounts it sees its own folder at the mount path, owned by that app's user, and other apps can't see it. On the volume that folder is `<mountPath>/.rigbox-apps/<app id>`, which is where you'll find it over SSH. Two apps that both list `volumes: [data]` don't see each other's files.

## Share a volume between apps

To let apps work on the same files, list them under `shared:` on the volume's `workspace.volumes` entry. Each listed app must also mount the volume in its own `volumes:`.

<Note>`shared:` needs the next CLI release.</Note>

Here `console`, `render` and `clips` share `uploads`, and `mail` can't mount it:

```yaml
workspace:
  volumes:
    - name: uploads
      mountPath: /home/developer/uploads
      sizeMb: 2048
      shared: [console, render, clips]

apps:
  console:
    path: ./console
    port: 5100
    start: npm start
    volumes: [uploads]
    visibility: public

  render:
    path: ./render
    port: 5101
    start: python3 render.py
    volumes: [uploads]

  clips:
    path: ./clips
    port: 5102
    start: npm start
    volumes: [uploads]

  mail:
    path: ./mail
    port: 5103
    start: npm start
```

`uploads` isn't the default `data` volume, so [create it](#declare-a-volume-in-rigyaml) on the stopped workspace before the first deploy.

### How access works

The listed apps see one shared folder at the mount path: `<mountPath>/.rigbox-shared` on the volume. Their app users join a group for that volume. The folder is group-writable (mode `2770`), and new files and folders in it are group-readable and group-writable whatever the app's umask. The folder isn't world-writable, new files in it aren't either, and apps that aren't listed can't reach it.

To take an app off the volume, remove it from `shared:` and remove the volume from its `volumes:`. The app loses access at the next deploy.

### Turning sharing on doesn't move data

Files an app wrote to its private folder stay there, at `<mountPath>/.rigbox-apps/<app id>` on the workspace, and the app no longer sees them at the mount path. Files already in the shared folder, `<mountPath>/.rigbox-shared`, get the volume's group the first time the volume is shared.

### Validation errors

The CLI refuses a `rig.yaml` that breaks these rules, and the error names the volume and the app:

- `shared:` lists at least one app, every app in it exists in this `rig.yaml`, and none is listed twice.
- Every listed app mounts the volume in its own `volumes:`.
- An app that isn't listed can't mount the volume.
- Only `workspace.volumes` entries can be shared. An app's own inline volume can't set `shared:`.

## Manage volumes with the CLI

You can also manage volumes independently of a deploy. Run locally, stop the workspace before create/resize/remove, then start it to attach the updated drive set:

```bash
rig workspace stop --workspace <WORKSPACE_NAME>
# create a volume (size in MiB, mounted at an absolute path)
rig volume create --workspace <WORKSPACE_NAME> --name data --size-mb 1024 --mount-path /home/developer/data
rig volume ls --workspace <WORKSPACE_NAME>                       # list volumes for a workspace
rig volume resize --workspace <WORKSPACE_NAME> --volume <VOLUME_ID> --size-mb 5120   # grow a volume
rig volume rm --workspace <WORKSPACE_NAME> --volume <VOLUME_ID>  # delete a volume (destroys its data)
```

<Note>
`rig volume resize` and `rig volume rm` take the volume id (from `rig volume ls`), not its name.
</Note>

Each command targets a specific workspace with `--workspace`:

```bash
# List volumes for a workspace
rig volume ls --workspace <WORKSPACE_NAME>

# Create a volume (size in MiB, with an absolute mount path)
rig volume create --workspace <WORKSPACE_NAME> \
  --name data \
  --size-mb 1024 \
  --mount-path /home/developer/data
```

<Warning>
Deleting a volume (`rig volume rm`) permanently destroys the data on it. This is separate from deleting the workspace — but deleting the workspace destroys its volumes too.
</Warning>

## The SQLite-under-$DATA_DIR pattern

The most common use is a SQLite database that outlives deploys. Two pieces make it work:

1. Set `DATA_DIR=/home/developer/data` in `env:` and put the database file under it.
2. `mkdir -p "$DATA_DIR"` at startup — a fresh workspace may not have the directory yet.

```python
import os, sqlite3

DATA_DIR = os.environ.get("DATA_DIR", "/home/developer/data")
os.makedirs(DATA_DIR, exist_ok=True)        # the dir may not exist on a fresh workspace
db = sqlite3.connect(os.path.join(DATA_DIR, "notes.db"))
```

Because `notes.db` lives on the volume, not in the synced app directory, an app release updates code while the database file remains on its separate disk.

<Tip>
To verify persistence, deploy the app, create some data, run `rig deploy` again, and confirm the data is still there. Verify the mount and data path; an environment variable alone does not create durable storage.
</Tip>
