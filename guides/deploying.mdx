Run the v0.13 CLI locally from a directory containing `rig.yaml`. Ordinary source deployments create managed app releases. For a runnable first project, follow [Deploy your first app](/quickstart).

## Prerequisites

Install the v0.13 CLI, run `rig login`, and confirm your app has install/start commands, a listening port, and an HTTP health endpoint. Use relative paths and put mutable data outside the managed release directory.

## 1. Create the manifest

Run `rig init` in your project, then review the generated values. The app name comes from `--name` or the directory name and is converted to lowercase letters, digits, and dashes, so the deploy accepts it; `rig init --name "My App"` writes `name: my-app`. Declare `workspace.deployment.strategy: incremental` for app releases. Check the [canonical manifest reference](/reference/rig-yaml) before deployment.

## 2. Deploy

```bash
rig deploy --name my-project
```

The CLI prepares a release, installs/builds its code, activates it, and checks affected apps. Keep `.rig.lock` so later deployments retain project identity and workspace bindings.

### What the release uploads

An incremental release uploads each app's source directory as it is on disk, skipping files the workspace already holds. It leaves out:

- credentials such as `.env`, `.env.*`, `.npmrc` and `.netrc`, dependency and build output such as `node_modules`, `.venv`, `target` and `dist`, and VCS metadata;
- whatever `.gitignore` ignores. In a git work tree git decides, so a file you have committed still ships. Outside one, for example in a `git archive` export, the `.gitignore` files are read directly;
- whatever a `.rigignore` lists.

A `.rigignore` uses `.gitignore` syntax and applies to its own directory and everything below it, so one at the project root covers every app. Unlike `.gitignore`, it also leaves out files you have committed:

```gitignore .rigignore
# Committed, but not needed at runtime
docs/
**/*.test.ts
web/.data/
```

Run `rig deploy -v` to list what each app left out and why. Workspace image deployments (`reproducible: true`) sync code with their own exclude list and don't read `.rigignore`.

If the API answers an upload or a status check with a temporary error (502, 503 or 504), or a connection drops, the CLI retries it a few times. If an upload still fails, nothing has been released or activated and the files already uploaded are kept, so running `rig deploy` again is safe and uploads only what is still missing.

<Note>`.rigignore`, the `-v` list of left-out files, and these retries need a CLI newer than 0.13.2. Earlier versions already skip git-ignored files inside a work tree.</Note>

## 3. Check the result

```bash
rig app ls --workspace my-project
rig app-release ls --workspace my-project
rig app health --app <APP_NAME> --output json
```

Use the actual app name and URL returned by Rigbox. Inspect every app outcome, not just the first URL. Read failed preparation or activation logs with `rig app-release logs --workspace my-project --release <RELEASE_ID>`.

## 4. Deploy a change

Run `rig deploy` from the same directory. Incremental activation briefly restarts affected services without replacing the workspace filesystem. Use [the development loop](/deploy/development-loop), [staging](/deploy/stage-and-activate), or [app rollback](/deploy/app-rollback).

## Configure a GitHub repository in the console

Follow [Deploy from GitHub](/guides/github). The console retains a reviewed deployment strategy; a manifest strategy must match that selection.

## How rig deploy resolves a workspace

An explicit `--workspace` targets a name or ID. Otherwise the CLI reuses the workspace binding in `.rig.lock` or creates a new workspace. Inspect bindings before reusing a checkout for another environment; specify the target explicitly when uncertain.

Inside a workspace, `rig deploy` deploys into that workspace. It ignores `.rig.lock` bindings, never creates a workspace, and refuses options that would clone, re-image, or replace the workspace it runs in; see [deploying from inside a workspace](/cli-reference/execution-modes#deploy-from-inside-a-workspace).

## The rig.yaml contract

The field reference now lives at [rig.yaml](/reference/rig-yaml). Keep a single canonical manifest per project.

### Single-app shape

Put `name`, `port`, `start`, and other app fields at the root. See [application fields](/reference/rig-yaml/application).

### Multi-app shape

Use a name-keyed `apps` map with a `path` for each local app. Do not mix root service fields with `apps`. Follow [multi-app projects](/deploy/multi-app).

## The health contract

Implement a successful HTTP readiness endpoint and declare its path/timeout. See [health checks](/configure/health). Incremental service releases currently require HTTP.

## Deploy modes

Choose explicitly between app releases and workspace images. See [deployment strategy](/reference/rig-yaml/deployment).

### Standard deploy

The v0.13 default source flow is an incremental app release, not a filesystem overlay. See [the development loop](/deploy/development-loop).

### Reproducible deploy

`reproducible: true` selects image deployment when no strategy is explicit. Use [reproducible builds](/deploy/reproducible-builds).

#### `build:` is always a command

`build: npm run build` is valid; Dockerfile/image mapping forms are not. See [commands](/configure/commands).

### Local source: freeze dependencies and sync code

This image workflow is described in [reproducible builds](/deploy/reproducible-builds). Incremental deployment instead prepares code in managed release directories.

### Git source: deploy the resolved commit

Git source uses the resolved revision; uncommitted local files are not a Git deployment input. See [source fields](/reference/rig-yaml/source) and [GitHub Actions](/guides/github-actions).

#### Pre-warm the image with `--build-only`

Run `rig deploy --strategy image --build-only` for an image build without deployment. See [build caching](/deploy/build-cache).

#### When to use which

Use [app releases](/deploy/overview) for ordinary code updates and [workspace images](/deploy/reproducible-builds) for a frozen environment.
