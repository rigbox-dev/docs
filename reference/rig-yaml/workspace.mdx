---
title: "Workspace fields"
description: "Declare the environment shared by an application project."
---

```yaml
workspace:
  deployment:
    strategy: incremental
  image: dev
  resources:
    ramMb: 2048
    vcpuCount: 2
    diskSizeMb: 10240
  env:
    NODE_ENV: production
  volumes:
    - name: data
      mountPath: /home/developer/data
      sizeMb: 1024
```

`image` and `resources` provide workspace creation defaults. They do not imply that an incremental deploy will replace or resize an existing workspace. Update resources separately and review image replacement explicitly.

`workspace.env` merges below each local app's environment. `workspace.secrets` merges by secret name, with an app's declaration taking precedence. Published `ref` apps use their recipe configuration rather than this local rendering merge.

For strategy selection and console differences, see [deployment fields](/reference/rig-yaml/deployment).

## Volumes

Each `workspace.volumes` entry declares a volume that local apps mount by name, for example `volumes: [data]`.

| Field | Shape and behavior |
| --- | --- |
| `name` | Name apps use in their `volumes` |
| `mountPath` | Absolute path where each app sees the volume |
| `sizeMb` | Size in MiB |
| `shared` | Optional list of app names that share one folder on the volume. Needs the next CLI release |

Without `shared`, each app that mounts the volume gets its own private folder at `mountPath`, which is `<mountPath>/.rigbox-apps/<app id>` on the volume. Other apps can't see it.

With `shared`, the listed apps see one folder at `mountPath`, which is `<mountPath>/.rigbox-shared` on the volume. Their app users join a group for the volume. The folder is group-writable (mode `2770`), new files in it are group-readable and group-writable, neither the folder nor new files are world-writable, and unlisted apps can't reach it. Removing an app from `shared` removes its access at the next deploy. Turning sharing on doesn't move files out of the apps' private folders; files already in `<mountPath>/.rigbox-shared` get the volume's group the first time it's shared.

```yaml
workspace:
  volumes:
    - name: uploads
      mountPath: /home/developer/uploads
      sizeMb: 2048
      shared: [console, render, clips]
```

A `rig.yaml` that breaks a `shared` rule is refused with an error that names the volume and the app:

- `shared` is a non-empty list of app names in this `rig.yaml`, without duplicates.
- Every listed app mounts the volume in its own `volumes`.
- An app that mounts the volume must be listed.
- Only `workspace.volumes` entries can set `shared`. An app's inline volume declaration can't.

A deploy doesn't create volumes: apart from the default `data` volume, create them on the stopped workspace before deploying. Choose mount paths deliberately and keep mutable data out of managed release directories. See [persistent volumes](/guides/persistent-volumes) and [share a volume between apps](/guides/persistent-volumes#share-a-volume-between-apps).
